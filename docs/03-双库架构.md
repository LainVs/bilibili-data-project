# 双库架构（D 写缓冲 / E 归档）

> 面向维护者。说明 D/E 两个 MySQL 实例的角色划分、连接选择与失败回退、
> 以及跨仓去重表的喂数链路。代码为权威来源，本文若与代码冲突以代码为准。

---

## 1. 为什么要有两个库

| | **D — 写缓冲库** | **E — 归档库** |
|---|---|---|
| 介质 | SSD | HDD |
| 角色 | 采集实时落库（高频写） | 查询 / 统计 / 分析（重读） |
| 内容 | 最新采集的 `bilibili_data`（全局表头库） | `bilibili_data` + 多个 `bilibili_<shard>` 小仓库 |
| 典型操作 | `upsert_*` 批量写 | 跨仓 `SELECT` / 聚合 / 全文检索 |

采集以高频小批量写入为主，落在 SSD 上的 D 库能扛住；统计与检索要扫全量历史
（HDD 容量大），落在 E。**D 攒够量后由归档流程切到 E**（见 §5），使 E 逐步
承载全量历史，同时 D 保持小而快。

> 单机单库也能跑：当 `[mysql_write]` 与 `[mysql_archive]` 指向同一 DSN 时，
> 系统自动识别为"单库模式"（`_uid_same_dsn()`），只查一次、不重复计数。

## 2. role 语义与别名

所有连接都经 `storage/db.py::get_conn(role)` 或 `storage/dao` 的
`_w()/_r()/_r_strict()` 获取。role 字符串存在历史别名，映射如下：

| 传入 role | 归属 | 配置节 |
|---|---|---|
| `write` / `buffer` / `d` | D 写库 | `[mysql_write]`（缺省回退 `[mysql]`） |
| `read` / `archive` / `query` | E 归档库 | `[mysql_archive]`（缺省回退 `[mysql]`） |

配置解析见 `config/__init__.py`：
- `mysql_write`：无 `[mysql_write]` 节则取 `[mysql]`
- `mysql_archive`：优先 `[mysql_archive]`，兼容旧名 `[mysql_read]`；两者都无则取 `[mysql]`
- `mysql_read` 是 `mysql_archive` 的别名（旧代码引用）

读超时更长：E 是 HDD，14M 级聚合 / 全文检索需要更宽松的超时
（`get_conn` 中 `read` 角色 `read_timeout=600`，写角色 `300`）。

---

## 3. 连接获取与失败回退（关键）

`storage/dao/__init__.py` 提供三个入口，语义**必须严格区分**：

| 入口 | 取哪个库 | E 离线时的行为 |
|---|---|---|
| `_w()` | D 写库 | 抛异常（写必须成功或显式失败） |
| `_r()` | E 归档库 | **静默回退到 D**（普通查询可用，但可能不全） |
| `_r_strict()` | E 归档库 | **抛 `EArchiveOfflineError`**，绝不偷查 D |

- 需要**全量语义**（统计总数、跨仓去重、榜单）时必须用 `_r_strict()`，
  否则 E 离线时回退 D 会给出偏小的错误结果。
- 只是"尽力查一下、拿不到就算了"的降级路径可用 `_r()`。
- 写路径一律 `_w()`。

异常类型：`StatsCancelled` 定义在 `storage/dao/_core.py`；`EArchiveOfflineError`
与 `StatsCancelled` 均由 `storage/dao/__init__.py` 对外暴露（前者定义于 `__init__`，
后者自 `_core` 重导出）。

### 线程级读连接复用

`_rcached(role, db, timeout)` 在**线程本地**（`_tls`）缓存同一
`(role, db, timeout)` 的连接，靠 `ping(reconnect=True)` 保活；坏连接由
`_drop_cached()` 丢弃重建。目的是避免跨仓查询时反复建连。调用方**不关闭**
复用连接，线程结束由 GC 回收。

## 4. shard（小仓库）

- 命名：`bilibili_<shard>`；`bilibili_data` 是**全局表头库**（不算 shard）。
- 列表：`storage/archive_sync.py::list_shards()` 从 `information_schema.schemata`
  查 `bilibili\_%` 并剔除 `bilibili_data`。
- 缓存：`_shard_dbs_trusted()`（`storage/dao/_core.py`）带 60s 缓存，返回
  `(shards, ok)`；**`ok=False` 表示本次列表拉取失败（用了兜底/缓存）**，
  调用方不得把结果当"全量"存进统计缓存——否则会把"暂时看不到的仓"误当"没有"。

---

## 5. 归档流程（D → E）

`storage/archive_sync.py::shard_archive()` 把 D 的增量切成 E 上的新小仓库：

1. D 的评论行数攒够 `_MIN_ROWS_FOR_NEW_SHARD`（200 万）才值得建新仓；
   已有**未完成** shard 时走**续拷**，不受此门槛限制。
2. 逐表（`_TABLES`）把 D 的数据导出、在 E 建 `bilibili_<shard>` 并导入。
3. **二次验对**：比对行数（容忍并发写入造成的 ±小漂移，非绝对相等）。
4. **清 D**：删掉已归档的行。按漂移量选择策略（`_choose_clear_strategy`）：
   - `truncate`：零漂移，秒清；
   - `reinsert`：小漂移（≤ `_DRIFT_REINSERT_MAX` 100 万行）→ 捞出漂移行 →
     `TRUNCATE` → 回插（比逐行 DELETE 快得多）；
   - `chunked`：大漂移或数量异常 → 逐批 DELETE（保守）。
   支持取消 / 逐批提交 / 心跳进度。

进度文件：`storage/shard_progress.json`（本机运行态，已 gitignore）。

## 6. 跨仓去重表（global_uids / global_comment_uids）

问题：同一个用户可能同时出现在 D、E 主库和多个 shard 里，直接 `SUM` 会重复计数。
解法：在 **E 主库 `bilibili_data`** 维护两张全库去重并集表（DDL 见
`storage/db.py::_GLOBAL_UIDS_DDL` 等，**只建在 E，不随小仓库复制**）：

- `global_uids(uid, uname)` —— 全库出现过的用户
- `global_comment_uids(uid)` —— 全库发过评论的用户
- `global_meta(k, v)` —— 覆盖标记（`backfill_shards` / `backfill_time`）

统计的 `users` / `comment_uids` 直接查这两张表（唯一精确来源）。

### 两条喂数链路（互补）

1. **直播喂数**（实时，best-effort）：写库成功后，`async_writer` 顺手调用
   `dao.add_global_comment_uids()` / `add_global_users()` 把 uid 写进 E 的去重表。
   E 离线则静默跳过（返回 0），不阻断主链、不进坏账。小批提交 +
   `_GLOBAL_WRITE_LOCK` 串行化，防并发连接堆积。
2. **归档 hook 回填**（补偿）：`shard_archive` 拷完一个 shard 后，调
   `dao.backfill_one_shard(shard)` 把该仓的 uid 并进全局表，并
   `_global_meta_add_shard()` 记覆盖标记。这样即使直播喂数期间 E 离线，
   历史 shard 也能补齐。`backfill_global_uids()` 可手动全量回填（有单实例锁
   `_BACKFILL_LOCK`，避免重复跑）。

`_global_coverage_ok()` 用 `global_meta` 判断覆盖是否完整：覆盖不全时统计
会标记 `_partial`，提示结果可能偏小，而不是假装精确。

## 7. 统计缓存

`stats_cache` 表（单行 JSON）缓存统计结果，避免启动时全表聚合。
写入前用 `_stats_plausible()` 校验；**列表拉取不可信（`ok=False`）时不得写缓存**，
否则会把一次网络抖动固化成长久的错误数字。

## 8. 跨仓检索的执行计划（索引 + 密度自适应）

跨仓搜评论的形态是 `WHERE content LIKE '%词%' ORDER BY ctime DESC LIMIT n`。
分仓建表用的 `_COMMENT_DDL` 里**没有 `idx_ctime`**，所以 19 个库每个都要全表扫
+ filesort，串行累加实测 **192 秒**。三处配套改动：

**① 补索引。** `idx_ctime (ctime)` 约 20 字节/行（1144 万行的仓占 0.23 GB）。
分仓 DDL 里刻意剔除这一行、改为**装载完成后**再建（`archive_sync.py` 的
「2.55 建检索索引」）——InnoDB 排序批量构建远快于边 `LOAD DATA` 边维护索引；
主库 `_COMMENT_DDL` 则保留。历史仓用 `tools/add_ctime_index.py` 补齐。

**② 密度自适应执行计划（`_plan_hint`）。** 单仓 1144 万行、`LIMIT 303` 实测：

| 关键词 | 命中/采样 2 万行 | 索引反扫 | 全表扫 |
|---|---|---|---|
| `的` | 7330（36.6%） | **0.0s** | 14.6s |
| `哈哈` | 127（0.64%） | **0.1s** | 14.3s |
| 零命中词 | 0 | 49.9s | **12.9s** |

纯加索引会让稀疏词慢 3.9 倍；且**优化器对 `LIKE '%x%'` 的选择率一律按 11% 估，
零命中词也会自发选索引计划**，所以不能靠它，必须显式给提示词。

做法：先用 `idx_ctime` 反扫采样 `_PROBE_ROWS`=2 万行数命中数（实测 0.06s）。
这段采样区间正是索引计划最先走的那一段，衡量的就是"凑够 n 条要扫多少行"。
稠密 → `FORCE INDEX(idx_ctime)`（反扫 + 早停）；稀疏 → `IGNORE INDEX(idx_ctime)`
（维持全表扫，不退化）。判据 `limit / density <= 表行数 × _INDEX_WALK_BUDGET`
（0.25，实测交叉点约 26%）。FULLTEXT 路径不给提示词，否则 `MATCH` 会找不到全文索引。

**③ 分仓倒序 + 提前终止（`_order_shards_fresh_first` / `_can_stop_early`）。**
`MAX(ctime)` 借 `idx_ctime` 反扫是 O(1)，据此按数据新鲜度倒序查分仓（新数据先出
首屏），并在「已凑满 limit 条、且剩余仓的最新评论都早于当前第 limit 名」时停止。
剩余仓不可能再有行挤进全局前 limit，所以是**精确**优化。任一仓时间未知即保守不停。

> **不要走并发路线**：实测并发查分仓只有 1.03x 加速（单查询反而变慢，磁头互相
> 寻道）。瓶颈是物理 I/O，不是 CPU。

## 9. 排查清单

| 现象 | 先看 |
|---|---|
| 统计数字偏小 | E 是否离线？`_global_coverage_ok()` / `_count` 的 WARNING 日志 |
| 按用户查很慢 | `idx_uid_ctime` 索引是否建成（`_migrate` 有 WARNING 就是没建成） |
| 按 UP 查超时 | `idx_owner` 索引是否建成 |
| 搜词很慢 | 分仓是否缺 `idx_ctime`：`python tools/add_ctime_index.py --dry-run` |
| 归档卡住 | `shard_progress.json` 与 `shard_archive` 日志；是否大漂移走了 chunked |
| 计数重复 | 是否误把 shard 与全局表一起 SUM（应只信 `global_*` 表） |
